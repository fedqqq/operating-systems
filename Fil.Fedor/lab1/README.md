# Лабораторная №1: Disk monitor, вариант 20 (15 баллов)

Автор: Фёдор Фил. Программа на C++17 запускает Linux-демон и отслеживает
события файловой системы через `inotify`. События направляются в `LOG_LOCAL0`,
а правило rsyslog сохраняет их отдельно в `/var/log/fil-fedor-disk-monitor.log`.
Служебные сообщения используют `LOG_DAEMON`.

## Сборка и запуск в Linux

Нужны Linux с `/proc`, ядро 5.3 или новее, g++ с поддержкой C++17 и rsyslog.
Сборка не требует сторонних C++-библиотек или прав root:

```sh
./build.sh
mkdir -p data/watched
./lab1
```

Скрипт компилирует все исходники в один `lab1` с `-Wall -Wextra -Werror`.
Промежуточная сборка удаляется автоматически, в том числе при ошибке.
Поддерживаются `CXX`, `CXXFLAGS`, `LDFLAGS`. Перед пересборкой остановите демон.

Для настройки отдельного журнала один раз выполните:

```sh
sudo cp rsyslog/30-fil-fedor-disk-monitor.conf /etc/rsyslog.d/
sudo systemctl restart rsyslog
sudo tail -f /var/log/fil-fedor-disk-monitor.log
```

Правило проверяет и facility `local0`, и имя программы: события других программ
в этот файл не попадают. `stop` исключает дублирование событий в общем журнале.
Сообщения о запуске, ошибках, перечитывании и остановке доступны через
`journalctl -t fil-fedor-lab1` или `/var/log/syslog` в зависимости от системы.
Сам демон может работать от обычного пользователя с доступом к наблюдаемым папкам.
Файл журнала открывает rsyslog, которому нужны соответствующие права.

## Конфигурация

По умолчанию используется `lab1.conf` в рабочем каталоге запуска:

```ini
# Одна строка на каждый корневой каталог
directory = data/watched
directory = /tmp/another-directory
```

Поддерживаются пробелы в путях, пустые строки, комментарии отдельной строкой
с `#`, окончания строк LF/CRLF. Кавычки, `~` и переменные окружения не раскрываются.
Каталоги должны существовать и быть доступны. Неизвестные ключи и пустой список
отклоняются. Дубликаты и каталоги внутри уже указанного корня объединяются.
Символические ссылки на каталоги внутри дерева не обходятся.

Путь к конфигу сохраняется как абсолютный **до** перехода демона в `/`.
Относительные каталоги отсчитываются от папки конфига. Конфиг можно заменять
атомарно по тому же имени. Наблюдение за `/var/log` и его родителями запрещено,
чтобы запись собственного журнала не порождала бесконечный поток событий.
У варианта 20 нет периодического интервала: события поступают от ядра сразу.

## Управление и демонизация

```sh
./lab1 /absolute/path/lab1.conf --pid-file /tmp/my-disk-monitor.pid
cat /tmp/my-disk-monitor.pid
kill -HUP "$(cat /tmp/my-disk-monitor.pid)"
kill -TERM "$(cat /tmp/my-disk-monitor.pid)"
./lab1 --help
```

Стандартный PID-файл — `/tmp/fil-fedor-lab1-<UID>.pid`, где UID — эффективный
идентификатор пользователя. Разные PID-файлы задают независимые экземпляры.

- `SIGHUP`: полностью проверить новый конфиг и установить новые наблюдения.
  При ошибке остаются прежние настройки, ошибка записывается в syslog.
- `SIGTERM` (также `SIGINT`): записать сообщение о выходе, закрыть inotify и
  освободить PID-файл.
- Повторный запуск с тем же PID-файлом: проверить `/proc/<PID>`, исполняемый
  файл и открытый PID-файл старого процесса, отправить ему `SIGTERM`, дождаться
  блокировки и записать новый PID после демонизации. Ожидание ограничено 10 секундами.
  Чужой живой процесс не останавливается. `pidfd` защищает отправку сигнала от
  повторного использования числового PID. Устаревший или повреждённый PID восстанавливается.

PID-файл блокируется через `flock` на всё время работы. После штатной остановки
он остаётся пустым: удаление файла создало бы гонку блокировок на разных inode.
Не удаляйте и не редактируйте PID-файл работающего экземпляра.

Класс `Daemon` — singleton с закрытым конструктором и запретом копирования.
Демонизация использует два `fork`, `setsid`, `chdir("/")`, `umask(0077)`,
закрытие унаследованных дескрипторов и перенаправление потоков 0–2 в `/dev/null`.
Родитель сообщает успех только после установки наблюдений и записи PID.
Неверный конфиг и ошибка начальной установки наблюдений не останавливают
предыдущий экземпляр.

Сигналы блокируются до `fork` и обрабатываются синхронно через `signalfd` и
`poll`. В асинхронных обработчиках не вызываются C++, работа с файлами или syslog.
Количество событий за один проход ограничено, чтобы поток файловых операций
не мешал обработке сигналов.

## События и рекурсивное наблюдение

Регистрируются `OPEN`, `ACCESS`, `MODIFY`, `ATTRIB`, `CLOSE_WRITE`,
`CLOSE_NOWRITE`, `CREATE`, `DELETE`, `MOVED_FROM`, `MOVED_TO`, `MOVE_SELF`,
`DELETE_SELF`, `UNMOUNT`, `IGNORED`. Строка содержит тип объекта, полный путь
и cookie, связывающий две стороны переименования:

```text
events=CREATE type=file path="/tmp/example/new.txt" cookie=0
```

Наблюдения устанавливаются для существующих подпапок и добавляются для новых
и перемещённых внутрь деревьев. При внутреннем переименовании пути обновляются.
При перемещении дерева наружу наблюдения снимаются; до завершения обработки
пары перемещения события покинувшего дерево подавляются. Имена с кавычками,
обратной косой чертой и управляющими символами экранируются.

Если сам корневой каталог удалён или перемещён, демон сообщает об этом.
После восстановления пути отправьте `SIGHUP`. Переполнение очереди inotify
явно записывается как потеря событий, после чего наблюдения перестраиваются.

Ограничения самого inotify: одинаковые ещё не прочитанные события могут
объединяться; установка наблюдений на новые подкаталоги не атомарна с их
созданием. Операции до установки watch и события, потерянные при переполнении,
восстановить нельзя. Это журнал полученных событий ядра, а не аудит каждого
системного вызова. Наблюдение не следует по символическим ссылкам и не
предотвращает изменения файлов другими процессами.

## Проверки в Linux и на macOS через Docker

Для полного воспроизводимого прогона используется отдельный Linux-контейнер
с настоящим rsyslog. На macOS запускать нужно именно так: inotify и `/proc`
принадлежат Linux.

```sh
docker build -t fil-fedor-lab1-test .
docker run --rm --init -v "$PWD:/lab" fil-fedor-lab1-test
docker run --rm --init -v "$PWD:/lab" fil-fedor-lab1-test python3 tests/demo.py
```

Демонстрация печатает настоящие PID, контекст процесса и строки журналов.
Результаты выполненных прогонов находятся в `verification/`.
Опция тестов `--isolated-syslog` поднимает rsyslog на свободном `/dev/log`
с **тем же правилом**, которое устанавливается в обычную систему. Она требует
root внутри отдельного контейнера и отказывается заменять существующий logger.
При уже настроенном системном журнале можно выполнить `./run_tests.sh`;
проверки отдельного служебного журнала будут отмечены как пропущенные.

Дополнительный прогон с проверкой памяти и неопределённого поведения:

```sh
docker run --rm --init -v "$PWD:/lab" \
  -e CXXFLAGS="-O1 -g -fno-omit-frame-pointer -fsanitize=address,undefined" \
  -e LDFLAGS="-fsanitize=address,undefined" \
  -e ASAN_OPTIONS="detect_leaks=1:halt_on_error=1" \
  -e UBSAN_OPTIONS="halt_on_error=1" fil-fedor-lab1-test
```

Тесты проверяют singleton, CLI, конфиги, реальную демонизацию и `/proc`,
унаследованные дескрипторы, файловые события, рекурсию, перемещения и замены
каталогов, символические ссылки, сигналы, восстановление после `SIGKILL`,
PID-файлы, одновременные запуски, работу без root, ошибку лимита дескрипторов,
500 файлов подряд и настоящее переполнение очереди. Проверка переполнения
пропускается при системном лимите очереди выше 32768; sysctl тесты не меняют.
Для дочерних демонов проверяются коды завершения и отчёты ASan/UBSan.
Временные файлы и процессы убираются после каждого сценария.
